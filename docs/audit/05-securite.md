# Agent 5 (Cybersécurité) : audit de sécurité du dépôt web avant l'app mobile

Périmètre : dépôt `BTM - Batir la Technologie de Mayotte` (HEAD `0b39a1e`, 64 commits), en lecture seule. Analyse statique, plus les tests SQL de sécurité lancés sur une base **locale** jetable. Je n'ai envoyé aucune requête à la production ni au projet Supabase distant. Aucune valeur de secret n'est recopiée ici.

## Résumé (5 lignes max)
- **Aucune vulnérabilité Critique confirmée.** Aucun secret n'a été commité, ni dans HEAD ni dans les 64 commits. RLS est activée sur les 29 tables. Les fonctions SECURITY DEFINER ont un `search_path` fixé et ne sont exécutables que par `service_role`. Les 94 tests SQL locaux passent : 0 échec, 0 faille connue.
- **Élevée (à vérifier)** : je ne peux pas confirmer que les migrations `20261120020000_ecritures_par_le_serveur` et `20261126000000_securite_serveur` sont appliquées **en production**. Le code masque leur absence (repli silencieux sur PGRST202). Si elles manquent, la clé publishable embarquée dans l'app permet d'écrire de faux messages et de faux souvenirs, et de dépasser le plafond du portefeuille.
- **Élevée (conception mobile)** : les routes `/api/**` n'authentifient que par **cookies** (`@supabase/ssr`), sans prise en charge de `Authorization: Bearer`. Sans adaptation côté serveur, l'app sera tentée de contourner les routes serveur, donc leurs quotas et leurs validations.
- Moyennes : pas de CSP ; IP du client lue dans `X-Forwarded-For`, sûr seulement derrière Vercel ; coût IA exposé par la création de comptes multiples et par `/api/aide` ouvert aux visiteurs ; rôle admin lu dans le JWT, encore valable jusqu'à 1 h après le retrait d'un délégué.
- Les deux points de l'agent Backend (UPDATE sans restriction de colonnes sur `conversations` et `profiles`) sont **confirmés mais de sévérité Faible** : aucune colonne sensible aujourd'hui (détail en C-12).

Toute logique de quota, d'IA ou de paiement reste côté serveur ; le mobile n'écrit jamais directement dans les tables.

- **P1** Rôle admin : relire le rôle à jour (`getUser()`) avant d'accorder l'exemption de quota dans `/api/chat`. Réduire la durée de vie du JWT ou vérifier le rôle à jour en RLS par une table `admin_roles` plutôt que par le claim (C-2).

### Exigences de sécurité pour l'app mobile Flutter
1. **Jetons** : stocker la session Supabase (access et refresh token) uniquement via `flutter_secure_storage` (Keychain sur iOS, Keystore et EncryptedSharedPreferences sur Android), avec un `LocalStorage` personnalisé pour `supabase_flutter`. Jamais dans `SharedPreferences`, jamais dans les journaux. Effacer la session à la déconnexion et à la réinstallation (`first_unlock_this_device`, sans sauvegarde iCloud ni Google).
2. **Clé publishable seulement** dans le binaire, considérée comme publique. **Aucune** clé secrète Supabase, IA, Stripe, SMTP ou OVH, et aucun `AI_KEYS_SECRET`, ni dans l'app, ni dans `--dart-define`, ni dans les assets. Tout ce que RLS laisse passer est accessible depuis un téléphone rooté : d'où la P0 sur B-5.
3. **Accès aux données** : lectures directes autorisées seulement sur les tables sûres (`conversations`, `messages`, `profiles`, `wallets`, `wallet_transactions`, `saved_addresses` : propriétaire uniquement). **Toutes** les écritures métier et tous les appels IA passent par les routes `/api/**` avec `Authorization: Bearer`.
4. **OAuth Google et deep links** : flux PKCE, avec un schéma dédié (`yt.btm.app://login-callback`) ou, de préférence, des **App Links / Universal Links vérifiés** (`assetlinks.json` et `apple-app-site-association` sur le domaine). Ajouter cette URL **exacte** dans les Redirect URLs de Supabase, sans joker. Ne pas réutiliser `/auth/callback` web pour le mobile. Utiliser Sign in with Google natif (`idToken` vers `signInWithIdToken`) avec un nonce si possible. Les liens de confirmation et de réinitialisation envoyés par e-mail doivent ouvrir l'app via App Links vérifiés, faute de quoi un autre paquet pourrait déclarer le même schéma et intercepter le lien.
5. **Coût IA et quotas** : quotas **par compte** côté serveur, comme aujourd'hui, et pas seulement par IP (CGNAT à Mayotte). Prévoir un identifiant d'appareil côté serveur et, à terme, une attestation d'application (Play Integrity, App Attest) sur `/api/chat`. Le plafond global de dépense (P1) est indispensable avant la publication sur les stores.
6. **Réseau** : HTTPS obligatoire (pas de `cleartextTraffic` sur Android ni d'exception ATS sur iOS). Le certificate pinning est facultatif, mais à éviter sans plan de rotation. Le domaine de l'API doit venir d'une configuration de build, pas d'une saisie de l'utilisateur.
7. **Paiement** : la recharge Stripe s'ouvre dans un navigateur système (Custom Tabs ou SFSafariViewController), jamais dans une WebView avec injection JavaScript. Le crédit n'est validé que par le webhook, comme aujourd'hui. Vérifier la conformité aux règles des stores sur les achats numériques (question à l'orchestrateur).
8. **Ce que le binaire peut contenir** : aucun prompt système, lexique ou consigne de Tamilya dans l'app, car ils seraient extractibles. Ils restent côté serveur.
9. **Révocation** : à la déconnexion, appeler `signOut(scope: global)` si l'utilisateur le demande. Après un retrait d'admin, tenir compte du délai d'expiration du JWT (C-2).
